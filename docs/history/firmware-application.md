# M4 application boundary

`firmware/src/application/application.c` wraps the accepted portable C sensing/control core without changing its model, gains or computations. It compiles into the Teensy diagnostic target and is exercised with a fake hardware abstraction layer. This is a reusable integration boundary, not a commissioned motor driver adapter.

The caller supplies timestamped raw motor SI samples, IMU samples, host references and independent power/stop/bus health. The application applies explicit encoder sign/zero and a checked proper IMU rotation, rejects discontinuities and repeated samples, calibrates stationary sensing, and schedules the estimator/controller and six command frames at 200 Hz. It builds each complete batch before queuing any frame. A missed 5 ms control deadline latches a fault; the fixed-step controller is never silently advanced with a longer elapsed interval.

The driver profile must document bus limits, codec, effort/gain units, encoder mapping, finite local effort enforcement, local PD/update/timeout behavior, CAN harness, IMU calibration and startup/stop timing. All nine attestations are required, but numeric flags alone cannot authorize hardware. A separately compiled host test admits clearly synthetic values; the production application rejects those values and any real profile while the generated hardware gate is false. All six drivers must acknowledge configured finite effort limits before arming. The HAL must enforce the documented local limits rather than assume a feedforward field bounds a retained PD command.

Host loss requests the existing bounded stop interval, then disables retained motor PD and discards queued batches. Restored host traffic does not rearm. Bus-off, stale/invalid sensing, missing profile/limit acknowledgment, invalid requests, transport rejection and timing faults latch inhibition. Fault and explicit reset remove power permission first; reset also cancels a prior active command batch and clears sensing/calibration. The hardware adapter's `disable_and_cancel_pending` contract includes both CAN queue cancellation and an actual qualified motor disable sequence.

The fake HAL checks calibration without motor frames, 200 Hz six-frame batches, eight latched failure classes, transport/deadline failures, controlled stopping, restart, invalid calibration/profile/range/axes, nontrivial sign/zero mapping, duplicate/discontinuous feedback and wheel/time wrap. Warning-clean host builds, UndefinedBehaviorSanitizer, Cortex-M7 compilation and the real Teensy target pass. The 10,000-packet core comparison remains identical to Python. These are software checks, not measured CAN/IMU/driver timing or full-physics validation of the new transport adapter.

The Teensy adapter keeps CAN listen-only, SILENT high and RUN_REQUEST low. Its send/disable callbacks are inhibited; operational ingestion/transport, bus-off interrupts, commissioning, heartbeat timing and driver acknowledgments still need exact hardware evidence and a separately reviewed adapter. The application heartbeat toggles every 10 ms only while its simulated permission/health conditions hold; that does not prove the external watchdog circuit or real MCU scheduling. No image has been flashed.

Reproduce with `tools/verify_completion_firmware.sh`. Configuration, comparison traces, build logs, target ELF/HEX and source/output hashes are saved in `artifacts/milestone-4/completion/firmware/`.

## Separate power-policy candidate

`firmware/src/policy/power_policy.c` is an isolated candidate, not a new operational HAL. It checks timestamped local temperatures, interval peak voltage and monotonic precharge/dump/positive-motoring energy counters. Startup reserves 1.2 J; braking reserves 10.5 J with 6.5 J held for the proposed bounded stop. Excessive positive stop work faults power permission even if dump energy remains low. A real adapter must cancel queued commands and retained driver PD within the declared response limits.

Cold boot and ordinary reset require cooldown; reset retains heat and meter history. Revoked qualification, invalid/stale/reset counters, thermal/peak/energy overload and missed startup/stop deadlines inhibit the policy. Production compilation rejects synthetic evidence and remains hardware-inhibited. Reproduce with `tools/verify_power_policy.sh`; configuration, traces and build hashes are in `artifacts/milestone-4/protection/firmware/`.

See [protection results](milestones/04-protection-results.md) for exact measurement assumptions and negative cases. The sampled stopping screen excludes the unpowered fall and increased-mass cases; it does not establish a future-stop guarantee. Integrating this policy into the application requires qualified meters, sensors, peak capture, independent startup cutoff, stopping-domain enforcement and an exact driver adapter. The accepted application/control core and diagnostic target remain unchanged.
